# Task Plan: task0007 — CLI argument handling vs GApplication

## Goal

Make `data-viewer <config-path>` reliably start the widget: the
application-specific positional argument must not be forwarded to
GApplication, where it is treated as a file argument and suppresses
activation.

## Requirements

FR2

## Scope

### Files to Create
- None.

### Files to Modify
- `internal/ui/ui.go` — do not forward application-specific arguments to the GTK application run call (pass only the program name, or equivalent)
- `cmd/data-viewer/main.go` — keep CLI parsing the single owner of app arguments; adjust the handoff if needed

## Design

Review finding addressed (reviews/round1.yaml): ffe893618eae5df9 (high).

- The config path is fully consumed by the entry point's own flag/argument
  parsing before the UI starts. The GTK application run call receives only
  the program name (index 0) so activation always fires regardless of user
  arguments.
- No GApplication command-line/open-files handling is introduced (out of
  scope; the app has exactly one optional positional argument).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The argument slice passed to the GTK run call never contains the config-path argument (unit-verifiable by extracting the args-preparation into a pure function, or by construction with a test asserting the constant).
- [ ] AC-2: Config-path resolution behavior (explicit arg > XDG) is unchanged and its existing tests still pass.
- [ ] AC-3: `go build ./...` and `go test ./...` pass; `gofmt` clean.
- [ ] AC-4: Manual M-1 launch check includes starting with an explicit config path argument.

## Test Notes

- Keep the args-preparation logic in a testable seam; GTK launch itself remains manual (M-1).

## Out of Scope

- New CLI flags; GApplication HANDLES_OPEN / command-line features.
