# Task Plan: task0002 — Deferred presentation & width-derived fitting (ui layer)

## Goal

The window is no longer shown automatically at activation: it is presented
exactly once, on request, already sized from the real row-packed layout at
the configured width — the width-0 degraded layout can no longer determine a
presented window's height.

## Requirements

FR1, FR5, NFR2

## Scope

### Files to Create
- `internal/ui/fit_test.go` — unit tests for the width-derivation and
  pre-map fitting logic (pure parts)

### Files to Modify
- `internal/ui/ui.go` — remove the unconditional presentation at activation;
  add the `Present` method per the IMPLEMENTATION.md Shared Components
  contract (first call wins, pre-frame calls honored at frame construction)
- `internal/ui/window.go` — width-derived pre-map fitting; map-time re-fit
  re-arms instead of silently no-oping before an allocation exists
- `internal/ui/sections.go` — row packing accepts an explicitly supplied
  available width so the pre-map path can pack against the derived width
  instead of the (absent) allocation

## Design

Presentation control (`Present` contract, IMPLEMENTATION.md):

- Activation builds the frame but does not show it.
- `Present` before the frame exists records the request; frame construction
  then completes it. Only the first effective call presents; later calls are
  no-ops. By IMPLEMENTATION.md decision 2, all first-data content updates
  scheduled before the present request have already been applied when it
  runs.
- Immediately before showing the window, run the pre-map fit (below) so the
  window maps at its final size (FR5, US1: no visible resize afterwards).

Pre-map fit (FR5, IMPLEMENTATION.md decision 3):

- Derive the content-area width from the configured window width minus the
  window's own CSS chrome — the same chrome accounting the existing refit
  uses for height, applied to the horizontal axis. Before any configured
  width exists, fall back to the window's current default width.
- Row-pack the sections against the derived width (explicit-width packing
  seam in the sections view) and measure the packed layout's natural height
  at that width; apply the existing minimum-height floor and monitor cap.
  Monitor geometry is unknown before realize; treat it exactly as the
  existing refit does (no cap when unknown).
- Postcondition: the height set before presentation equals what the
  allocation-driven refit would compute for the same width — assert this
  agreement in a unit test over the shared pure computation.

Steady-state safety net:

- The map-signal deferred re-fit currently no-ops permanently when it runs
  before the first allocation. Change it to re-arm (retry on a later
  main-loop iteration) until an allocation exists, then fit once. All other
  existing triggers stay untouched.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Activation alone never shows the window; it appears only after
      the present request (FR1).
- [ ] AC-2: A present request arriving before frame construction is honored
      when the frame is built; the first effective request presents; later
      requests are no-ops.
- [ ] AC-3: The height applied at presentation is computed by packing the
      sections at the width derived from the configured width — given a
      configured width, the pre-map computation and the allocation-driven
      computation produce the same height for the same inputs (unit test on
      the shared pure logic).
- [ ] AC-4: A layout packed at width 0 (degraded one-per-row) is never the
      source of a presented height: the pre-map fit path demonstrably packs
      at the derived width (FR5).
- [ ] AC-5: The map-time deferred re-fit retries until an allocation exists
      instead of no-oping permanently (observable via the pure retry-decision
      logic).
- [ ] AC-6: Existing steady-state behavior is preserved: update-driven
      refit, style/settings-driven refit, and monitor-change re-cap paths
      remain wired (compile-level/wiring assertions plus manual checklist).
- [ ] AC-7: `go test ./internal/ui/...` and `go build ./...` pass; new pure
      logic carries unit tests, GTK-touching glue stays thin (NFR2).

## Test Notes

- Pure and testable: width derivation (configured width → content width),
  agreement between pre-map and allocation-driven height computation
  (AC-3), degraded-layout exclusion (AC-4 via packing-input assertions),
  retry decision (AC-5).
- GTK-touching parts (Present timing, map signal wiring) are excluded from
  automated tests per test/README.md; they are covered by VERIFICATION.md's
  manual scenarios.
- Existing tests in `window_test.go` / `sections_test.go` must keep passing;
  extend them where the packing seam changes signatures.

## Out of Scope

- When to present (readiness accounting, timeout) — task0001 owns the gate.
- Any change to the runner or the app-layer event flow.
- Changing steady-state trigger semantics beyond the map-time re-arm.
