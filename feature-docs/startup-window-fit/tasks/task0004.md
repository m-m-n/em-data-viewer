# Task Plan: task0004 — Review round 2 fixes (projection-before-runner ordering, repeat-activation raise)

## Goal

The startup sequence can no longer present a window whose section content
was discarded by the projection race: the initial UI projection and the gate
arming are ordered before the runner starts emitting events. A repeat
application activation raises the already-presented window again.

## Requirements

FR1, FR2

## Scope

### Files to Create
(none)

### Files to Modify
- `internal/app/reload.go` — order the projection dispatch and gate arming
  before the runner apply in the success path
- `internal/app/app_test.go` — ordering assertions for the new sequence
- `internal/ui/ui.go` — repeat-activation raise of the presented window

## Design

Fix 1 — projection before runner (review findings 26b3ce832cd1a156,
86803c68798485df): in the success path the runner is currently started
before the UI projection is queued and before the gate is armed, so a fast
first event's UI update can be scheduled ahead of the section-widget
creation and be silently ignored, while its receipt still satisfies the
gate — presentation with unapplied data. Reorder the success path so that,
in this order: the UI projection (banner clear, window settings,
keep-above, section view models, rehydrations) is dispatched first, the
gate is armed second, and the runner apply runs last. Consequences to
preserve and assert:

- Every runner event is now necessarily scheduled after the projection on
  the FIFO dispatch, so section updates always find their widgets.
- The gate is armed before any event can be received; the pre-arm receipt
  buffer (task0003) remains as a safety net and its tests stay valid.
- The present request still queues strictly after the gate-completing
  event's UI update (existing FIFO guarantee, unchanged).
- The stale-reload guard semantics are unchanged: the projection dispatch
  keeps its generation gating; arming stays one-shot (first successful
  apply only), so a stale reload still cannot arm or re-arm the gate.

Failure path (load error) is untouched.

Fix 2 — repeat-activation raise (finding 454d0fb9e0a99942): when the
activate handler finds an existing frame, it currently does nothing, so a
second launch of the single-instance application no longer brings the
window to the front (pre-task0003 behavior did). In that branch, when the
window has already been presented, present the existing window again to
raise it; when it has not been presented yet (gate not fired), keep doing
nothing so the hidden frame stays hidden. No refit is re-run — this is a
raise, not a re-fit.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: In the success path, the projection dispatch, the gate arming,
      and the runner apply are invoked in exactly that order (verified with
      recording fakes).
- [ ] AC-2: With a FIFO dispatcher, a runner event consumed immediately
      after apply produces its section update after the projection callback
      — no update is lost to missing widgets (ordering test at the app
      layer).
- [ ] AC-3: All existing gate tests (including the pre-arm buffer tests)
      and reload/consume tests keep passing unmodified in their assertions
      (mechanical call-site updates only where signatures/ordering fakes
      require).
- [ ] AC-4: The activate handler with an existing frame presents the window
      again only when it was already presented; before first presentation
      it still does nothing (the hidden frame is never revealed early).
- [ ] AC-5: `go build ./...` and `go test ./...` pass; existing tests are
      not weakened or removed.
