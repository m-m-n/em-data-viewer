# Task Plan: task0001 — Startup readiness gate (app layer)

## Goal

The app layer decides when the window may first be shown: after every
section's first data arrived, after the fixed 1-second timeout, or
immediately when there is nothing to wait for — and requests presentation
from the ui layer exactly once.

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2

## Scope

### Files to Create
- `internal/app/gate.go` — startup readiness gate: tracked section keys,
  first-data accounting, timeout decision, one-shot ready callback
- `internal/app/gate_test.go` — unit tests for the gate

### Files to Modify
- `internal/app/app.go` — construct the gate, define the app-side
  presenter seam (type-assertion helper per IMPLEMENTATION.md Shared
  Components), wire the ready callback to a dispatched present request
- `internal/app/events.go` — notify the gate of each section's first
  received event at receive time (before scheduling that event's UI update
  is completed for the final section, the present dispatch must be queued
  after it — see ordering decision)
- `internal/app/reload.go` — on the FIRST successful config application, arm
  the gate with the section keys; on a first-load failure or a zero-section
  config, tell the gate to fire immediately

## Design

Gate responsibilities (GUI-free, own file):

- Holds the set of section keys still owing their first data.
- `markReceived(key)`: removes the key regardless of event kind — replace,
  append, and error all count (FR2). Unknown keys are ignored.
- Fires its ready callback exactly once, on whichever comes first: the owed
  set becoming empty, the timeout elapsing (FR3), or an explicit
  immediate-fire request (FR4). Later triggers are no-ops (one-shot; also
  covers live reloads per IMPLEMENTATION.md decision 4).
- The timeout duration is injectable; production wiring passes the fixed
  1-second constant (FR3 — not configurable). The timeout must be
  event-driven (timer callback), not polled (NFR1).
- Arming is one-shot too: only the first successful config application arms
  the gate; subsequent reloads must not re-arm or re-fire.

Wiring flow:

1. Reload projection (first successful apply): arm the gate with the applied
   section keys and start the timeout. First-load failure or zero sections:
   request immediate fire (FR4).
2. Event consumer: on receiving a runner event, schedule its UI update
   (existing behavior), then mark the key received. When that mark completes
   the gate, the gate's ready callback runs and dispatches the present
   request through the same main-loop dispatch seam — strictly after the
   just-scheduled UI update (IMPLEMENTATION.md decision 2).
3. The dispatched present request calls the presenter seam: a type assertion
   on the app's `UI` interface value for a `Present()` method, no-op when
   unimplemented (mirrors the existing keep-above assertion helper).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: When every armed section key has been marked received, the ready
      callback fires exactly once.
- [ ] AC-2: An error event's key counts as received, exactly like a success
      event's (FR2).
- [ ] AC-3: The gate is kind-agnostic: a stream section's first append event
      marks it received (FR2).
- [ ] AC-4: With keys still owed, the ready callback fires when the injected
      timeout elapses (FR3).
- [ ] AC-5: Arming with zero keys, and the explicit immediate-fire request,
      each fire the ready callback without waiting (FR4).
- [ ] AC-6: After the callback has fired once, further marks, timeouts,
      immediate-fire requests, and re-arm attempts never fire it again.
- [ ] AC-7: The present request is dispatched through the main-loop dispatch
      seam after the gate-completing section event's UI update was scheduled,
      so a FIFO dispatcher applies that update first (verified with a
      recording dispatcher).
- [ ] AC-8: The presenter seam is a no-op when the UI value does not
      implement the present method, and calls it when it does.
- [ ] AC-9: `go test ./internal/app/...` passes with no GTK dependency in
      the new code (NFR2).

## Test Notes

- All criteria are unit-testable with the existing app-layer test style:
  fake UI, synchronous or recording dispatch function, injected timeout
  duration (use a short duration in tests; never sleep-poll).
- Concurrency edge worth covering: timeout firing concurrently with the last
  `markReceived` — exactly one ready invocation (AC-6 corollary).
- AC-7 uses a recording dispatcher asserting relative order of the two
  scheduled callbacks.

## Out of Scope

- The ui-layer present implementation and any size computation (task0002).
- Any change to runner event kinds or the coalescing logic beyond notifying
  the gate.
- Persisting or configuring the timeout.
