# Task Plan: task0003 — Review round 1 fixes (gate ordering, width clamp, activation, retry bound)

## Goal

The four defect groups confirmed by review round 1 are fixed: the readiness
gate no longer loses first-data events that arrive before arming, the derived
content width is always positive, a repeat application activation no longer
strands the visible window, and the map-time re-fit retry is bounded.

## Requirements

FR1, FR2, FR5

(none)

- `internal/app/gate_test.go` — tests for event-before-arm ordering

- `internal/ui/window.go` — positive width clamp; bounded map-refit retry

## Design

Fix 1 — order-independent readiness (review findings b690fe0ec7573b25,
f78c485ec1383324, 9aef0f0861f8caa8, 22339b4c67da299b): the gate currently
ignores `markReceived` for keys not yet armed, but in production the runner
(event source) starts before `arm` runs, so a fast section's first event can
be lost, delaying presentation to the timeout. Make the gate retain receipts
that arrive before arming and reconcile them against the owed set when `arm`
runs (fire immediately when the reconciled owed set is already empty). This
keeps the callers' existing call order — no change to the reload projection
or event consumer wiring. One-shot semantics and the FIFO
present-after-projection ordering are unchanged.

Fix 2 — positive derived width (finding a4ca638691b48386): the
configured-width-to-content-width derivation currently returns the raw
subtraction, which can be non-positive when the configured width does not
exceed the window chrome; a non-positive width would re-enter the forbidden
degraded packing at presentation time. Clamp the derivation to a positive
floor so packing always runs against a usable width (FR5's "derived content
width must always be positive").

Fix 3 — repeat activation (finding 6ff3de2d6683a663): the activate handler
unconditionally replaces the frame, so a second activation of the
single-instance application swaps all subsequent UI updates onto a hidden
frame while the visible window goes stale. When a frame already exists,
keep it (no new frame, no re-registration); the handler's presentation
bookkeeping stays as is.

Fix 4 — bounded map-refit retry (finding 3b93f2acf0fd701d): the map-time
re-fit currently re-arms itself unconditionally while no allocation exists,
which can busy-spin the main loop in degenerate geometries. Bound the retry
(attempt cap; give up silently after it — presentation already applied the
pre-map fit, this path is a safety net). The retry decision stays in pure,
unit-testable logic.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A key marked received BEFORE `arm` counts: arming with exactly
      that key fires ready immediately; arming with that key plus others
      leaves only the others owed (event-before-arm ordering test).
- [ ] AC-2: Pre-arm receipts never fire the callback themselves, and
      one-shot semantics are preserved across the new path (a fired gate
      ignores later arms/marks as before).
- [ ] AC-3: The width derivation never returns a value below its positive
      floor, for any combination of configured width, fallback width, and
      chrome (including chrome ≥ width).
- [ ] AC-4: When the activate handler runs with an existing frame, the
      frame is not replaced (repeat activation keeps the visible window as
      the target of subsequent updates); first activation behavior is
      unchanged.
- [ ] AC-5: The map-refit retry decision reports "retry" at most a bounded
      number of times for a never-allocating widget, then reports "stop"
      (pure-logic test).
- [ ] AC-6: `go build ./...` and `go test ./...` pass; existing tests are
      not weakened or removed.
