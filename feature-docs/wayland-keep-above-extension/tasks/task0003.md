# Task Plan: task0003 — Review round 1 fixes (either-id matching, PID verification, enable failure propagation)

## Goal

Fix the three review round 1 findings: premature non-match finalization
when only one window identifier has arrived (finding 30df4ac583821833),
missing process-identity verification before setting a window above
(34d210ad32419055), and silently suppressed enable failures for
known installs in `install-extension` (272c51154d0baa96).

## Requirements

FR2, FR5

## Scope

### Files to Create
- None

### Files to Modify
- `contrib/gnome-shell-extension/keep-above@em-data-viewer.m-m-n.github.io/extension.js`
  — either-id matching semantics + process-identity verification
- `Makefile` — `install-extension` enable-failure handling

## Design

See IMPLEMENTATION.md Shared Components for the UUID / target app id
literals, and SPEC.md FR2 (revised) for the matching contract.

### Either-id matching (FR2 revision)

The current decision flow treats the first non-empty identifier (GTK
application id, else window class) as final. Revise the per-window
decision so that:

1. A window MATCHES as soon as either identifier equals the target id.
2. A non-match is FINAL only when both identifiers are set and neither
   matches, or the window becomes unmanaged. While one identifier is
   still unset, the per-window watch stays attached and re-evaluates on
   either identifier's change notification.
3. On any final decision (match applied, both-set non-match, unmanaged)
   the per-window watch is detached, exactly as today.

### Process-identity verification (FR2 addition)

A single decision point (shared by the enable-time scan, window-created
path, and re-check path) verifies, after an id match and before setting
the window above: the compositor-reported PID of the window resolves —
via the proc filesystem — to an executable whose file name is
`em-data-viewer`. No PID, unreadable process info, or a different
executable name → the window is NOT set above (and the decision is final
for that check; no retry loop). The disable-time revert loop is unchanged
(SPEC FR4 as written).

### Enable failure propagation (FR5, Makefile)

In `install-extension`, tolerate a failing enable command ONLY in the
detected fresh-install case (where the re-login guidance is printed). In
the known-install case (`fresh=0`) a failing enable must fail the target
with a message naming the enable step, and the enable command's error
output must not be discarded in that case. Existing behaviors (tool
probe, fresh detection before the copy, idempotent copy, guidance
message, exit 0 on success paths) are unchanged.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A window whose first-arriving identifier is a non-target
      value and whose other identifier later arrives with the target id
      is matched and set above (watch not detached on the first
      non-matching value while the other identifier is unset).
- [ ] AC-2: A window is set above only when its compositor-reported PID
      resolves to an executable named `em-data-viewer`; verification
      failure (no PID / unreadable / different name) leaves the window
      untouched. All three apply paths (enable scan, window-created,
      re-check) go through this verification.
- [ ] AC-3: `install-extension` with a known install (`fresh=0`) fails
      non-zero with a message when the enable command fails; the
      fresh-install case still tolerates enable failure, prints the
      re-login guidance, and exits 0.
- [ ] AC-4: Per-window watches are still detached on match, on both-set
      non-match, and on unmanage; `disable()` still detaches every
      remaining watch (no handler leak).
- [ ] AC-5: `go build ./...`, `go test ./...`, `gofmt -l -w .` results
      unchanged; no Makefile target other than `install-extension` is
      modified.
