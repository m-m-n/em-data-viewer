## Design

See SPEC.md FR2 / FR4 (revised) for the contracts.

### Tracked revert set (FR4 revision)

Whenever the extension actually sets a window above, record that window in
a collection owned by the extension instance. `disable()` reverts
(`unmake_above()`) exactly the recorded windows that still exist, instead
of re-deriving "matching windows" with a separate matcher. Windows leave
the collection when they are unmanaged (reuse the existing unmanage
handling; a destroyed window must not linger in the collection or be
touched at disable time). The revert loop no longer consults identifiers
or process verification at all — apply set and revert set are the same
set by construction.

### Deleted-marker tolerance (FR2 detail)

Before comparing the resolved executable name, strip a trailing
` (deleted)` marker (the kernel appends it to the proc exe link when the
on-disk binary was replaced or deleted). Comparison target and all other
verification failure semantics are unchanged.

### Shell-recognition fresh detection (FR5 alignment)

In `install-extension`, base the fresh/known decision SOLELY on whether
the uuid appears in the CLI's extension list — directory existence no
longer participates. Known (uuid listed) + enable failure → the target
fails non-zero (existing round-1 behavior); unknown uuid → enable failure
tolerated + re-login guidance. Everything else about the target
(tool probe, idempotent copy, message texts, exit codes on success)
stays as is.
