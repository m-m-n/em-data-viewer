# Task Plan: task0002 — Ctrl+T toggle state and key controller

## Goal

The live window remembers which background pattern is active, flips it when
the user presses `Ctrl+T` with the window focused, and re-applies the
stylesheet immediately without touching geometry, config, or any other input
behavior.

## Requirements

FR4, FR5, FR6, FR7, FR8, NFR2, NFR3

## Scope

### Files to Create
- (none)

### Files to Modify
- `internal/ui/window.go` — active-pattern state, the key controller and its
  pure match rule, and the restyle path that applies the pattern.
- `internal/ui/window_test.go` — tests for the pure match rule and the state
  flip.

## Design

### Active-pattern state

The frame gains one process-local field recording whether the alternate
pattern is active. It starts false (primary active) when the frame is
constructed, and is never read from or written to the config file
(IMPLEMENTATION.md Shared Components, FR5).

### Applying the pattern

The frame's existing restyle path currently hands its merged window style map
straight to the stylesheet builder. It must instead hand over the result of
the `ApplyBackgroundPattern` rule (contract in IMPLEMENTATION.md Shared
Components) for the current state. Because the merged map itself is never
rewritten, re-applying window settings on a config reload leaves the active
pattern untouched (FR8, IMPLEMENTATION.md D2) — no extra bookkeeping in the
settings path is needed, and none should be added.

### Toggle

Flipping the state and then running the existing restyle path is the whole
toggle. Restyle only reloads the CSS provider — it does not re-measure, re-fit
or re-pack — so geometry cannot change as a side effect (NFR3). The toggle
must be safe to invoke before the window has been presented or realized: it
only mutates a field and reloads a provider that already exists at
construction time.

### Key controller and match rule

Attach a key controller to the application window, in the same capture-phase
style the existing scroll blocker and drag-to-move gesture use, so no child
widget can swallow the event first (IMPLEMENTATION.md D4).

Factor the decision into a pure predicate taking the pressed key value and
the event's modifier state, so it is testable without GTK:

1. Accept only when the key value is the `t` key (both the lowercase and the
   uppercase key values must be accepted, since a keyboard with Caps Lock or
   Shift engaged reports the uppercase value).
2. Accept only when the control modifier is present.
3. Reject when the alt or super modifier is present, so distinct bindings
   (e.g. a compositor's Ctrl+Alt+T terminal shortcut) are never stolen.
4. Reject everything else — any other key value, and `t` with no control
   modifier.

The controller claims the event only when the predicate accepts; on any other
event it must leave the event unclaimed so drag-to-move, the right-click
context menu, and the existing scroll blocking behave exactly as before
(FR7).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The match rule accepts the lowercase and uppercase `t` key values
      when the control modifier is present and neither alt nor super is.
- [ ] AC-2: The match rule rejects: `t` with no control modifier, `t` with
      control plus alt, `t` with control plus super, and unrelated key values
      with control held.
- [ ] AC-3: The state flip toggles primary → alternate → primary across
      repeated invocations, with no accumulated drift.
- [ ] AC-4: A newly constructed frame reports the primary pattern as active.
- [ ] AC-5: Toggling produces a window stylesheet whose window background is
      the alternate value, and toggling back restores the primary value,
      while every other emitted style declaration is unchanged.
- [ ] AC-6: Re-applying window settings (the config-reload path) while the
      alternate pattern is active leaves the alternate pattern active, and
      the newly supplied alternate value is what the stylesheet then carries.
- [ ] AC-7: No config write occurs as a result of toggling.

## Test Notes

AC-1 through AC-3 are pure-function unit tests with no GTK involvement. AC-4
through AC-6 concern frame state; where constructing a real frame requires a
display, test the underlying state-plus-selection composition directly
against the stylesheet builder rather than driving GTK — the existing
`internal/ui` tests are the precedent for what can and cannot run headlessly.
AC-7 is satisfied by construction (the toggle path has no config dependency);
assert it structurally rather than by observing the filesystem.

The keyval constants and modifier flags come from the toolkit bindings
already in use; no new dependency is required.

## Out of Scope

- The `background_alt` default, the design token, the selection rule itself,
  and the example-config documentation (task0001).
- Persisting the toggle state, exposing it in the context menu, or adding any
  other binding.
- Changing drag-to-move, the context menu, scroll blocking, or the window
  fit/reflow logic.
