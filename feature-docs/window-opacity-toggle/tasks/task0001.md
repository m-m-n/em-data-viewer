# Task Plan: task0001 — Alternate background value, token, and selection rule

## Goal

The style layer knows a second window background pattern: it has a default,
a matching design token, it accepts a user override, and it exposes the pure
rule that decides which of the two patterns a stylesheet renders.

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2

## Scope

### Files to Create
- (none)

### Files to Modify
- `design-system/tokens.yaml` — add the `color.surface-alt` token.
- `internal/ui/style.go` — add the `background_alt` window style default and
  the pure background-pattern selection rule.
- `internal/ui/style_test.go` — tests for the new default, the override path,
  the selection rule, and the token drift guard.
- `config.yaml.example` — document the new key alongside `background`.

## Design

### Token

Add a role-based color token named `surface-alt` next to the existing
`surface` token, with value `#1e1e1e99` and a description stating it is the
alternate, more transparent widget-window background selected by the runtime
toggle (the primary value stays `surface`). The existing drift-guard test
compares the token file against the runtime default tables, so the token
value and the runtime default must be the same literal string.

### Window style default

Add `background_alt` to the window style default table with the value
`#1e1e1e99`. Adding it to that table is what makes the merge rule accept
`window.style.background_alt` from user config: the merge rule ignores any
key absent from the defaults. No alias entry is needed — the user-facing key
name and the internal key name are identical, exactly as for `background`.
The drift-guard test resolves the runtime default for this key from the new
token, so the test's key-to-token mapping must be extended alongside it.

### Selection rule

Provide the `ApplyBackgroundPattern` rule described in IMPLEMENTATION.md
Shared Components. Behavior:

1. Given a merged window style map and a flag stating whether the alternate
   pattern is active.
2. When the flag is false, the caller must observe the input's `background`
   value.
3. When the flag is true, the caller must observe the `background_alt` value
   in the place the stylesheet reads the window background from.
4. The input map is never mutated — callers hold the merged map across the
   process lifetime and re-use it on every restyle.
5. When no `background_alt` entry exists at all (a caller that built its map
   without the defaults), the primary value is kept rather than emitting an
   empty background.

Every other entry — frame color, frame width, radius, error color, error
background — passes through unchanged, so the toggle can never affect layout
or the error banner (IMPLEMENTATION.md D3).

### Example config

Document `background_alt` in the commented example config next to the
existing `background` line, stating that it is the second transparency
pattern and that `Ctrl+T` switches between the two. Keep the example's
current default appearance unchanged: the primary value stays as it is.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Merging a window style with no `background_alt` override yields
      the default value `#1e1e1e99` for that key, and leaves `background`
      at its existing default.
- [ ] AC-2: Merging a window style with a user `background_alt` override
      yields the overridden value, and does not affect `background`.
- [ ] AC-3: The selection rule with the alternate flag false produces a
      window background equal to the map's `background` value; with the flag
      true it produces the map's `background_alt` value; in both cases every
      other style entry is identical to the input.
- [ ] AC-4: The selection rule does not mutate the map it is given (the
      caller's map is byte-identical before and after a call with either
      flag value).
- [ ] AC-5: The selection rule with the alternate flag true, applied to a map
      that has no `background_alt` entry, produces the map's `background`
      value.
- [ ] AC-6: The existing token/runtime drift-guard test passes with
      `color.surface-alt` present and covers the new `background_alt` key.
- [ ] AC-7: `config.yaml.example` documents `background_alt`, and the example
      config still loads without error.

## Test Notes

Everything here is unit-testable without GTK: the merge rule, the selection
rule, and the drift guard already have table-driven tests in
`internal/ui/style_test.go` — extend those tables rather than adding parallel
ones. Edge cases worth explicit cases: absent `background_alt`, an override
equal to `background`, and non-mutation of the input map. The example-config
load check belongs with the config package's existing example-file test if one
exists; otherwise assert the documented key round-trips through the window
style merge.

## Out of Scope

- Any key handling, toggle state, or window/frame change (task0002).
- Validating color syntax — style values stay pass-through user input.
- Applying the alternate pattern to the error banner, border, or sections.
