# Task Plan: task0001 — Dynamic window height & config height removal

## Goal

The window height is derived from the content's natural height (banner +
sections), follows content changes at runtime, and is capped at the monitor
height; the `window.height` config field is removed end-to-end.

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2

## Scope

### Files to Create

None.

### Files to Modify

- `internal/config/config.go` — remove the window height field from the
  config model and its default constant
- `internal/config/load.go` — remove the height field from the YAML schema
  struct and its default/copy logic (non-strict decoding then silently
  ignores a `height` key)
- `internal/config/load_test.go` — update/add cases: YAML containing
  `window.height` loads without error and without effect; YAML without it
  loads as before
- `internal/app/reload.go` — stop passing a height when translating config
  into the ui layer's window settings
- `internal/ui/ui.go` — remove the height field from the window-settings
  type
- `internal/ui/window.go` — dynamic height: size the window to content,
  re-fit on content changes, cap at monitor height; width-only default size
- `internal/ui/style_test.go` — update if any height plumbing is referenced
- `config.yaml.example` — drop the `height` line

## Design

### Config layer (FR4, NFR1)

- Remove the height field from both the parsed config model and the YAML
  schema struct, plus the height default constant. Because YAML decoding is
  non-strict, a `height` key present in a user's file is silently ignored —
  no error, no warning, no log line.
- Width, style, and keep-above handling are untouched.

### App layer

- The config-to-ui translation passes width and style only.

### UI layer (FR1, FR2, FR3, NFR2)

- The window's height must never be fixed by a default size; only the width
  comes from settings. The window's height derives from the natural height
  of the root box (banner + sections view).
- **Shrink requirement**: a resizable GTK4 toplevel keeps its larger size
  when content shrinks, so the implementation must actively re-fit the
  window height whenever content height may have changed (section content
  update, section add/remove, banner show/hide, style change, config
  reload). The existing reflow-trigger wiring shows where such change
  notifications already flow.
- **Monitor cap (FR3)**: on re-fit, the target height is
  min(content natural height, monitor height), where the monitor is the one
  the realized window is on. Overflow beyond the cap is clipped — no
  scrollbar. Before the window is realized (no monitor known), no cap is
  applied.
- **Minimum height (NFR2)**: the existing minimum frame height (48px) so a
  zero-section window stays grabbable is preserved.
- Drag-to-move, keep-above, context menu, and all styling behavior are
  untouched.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Loading YAML that contains a `window.height` key succeeds with
      no error, and the loaded config exposes no height value (compile-time:
      the field no longer exists).
- [ ] AC-2: Loading YAML without `window.height` behaves exactly as before
      for all remaining fields (width default 400, style, keep_above).
- [ ] AC-3: The config package builds and tests headlessly (`go test ./...`)
      with no GTK imports.
- [ ] AC-4: `config.yaml.example` contains no `height` line.
- [ ] AC-5: The ui window-settings type has no height field; the window's
      default size is set from width only (manual/GUI verification for the
      rendered result).
- [ ] AC-6: Manual: with a running window, growing section output makes the
      window taller; shrinking output (or removing a section via config
      reload) makes it shorter.
- [ ] AC-7: Manual: content taller than the monitor caps the window at the
      monitor height with the overflow clipped.
- [ ] AC-8: Manual: with zero sections the window still shows at the minimum
      frame height and remains draggable.

## Test Notes

- AC-1/AC-2 are table-driven unit tests in the config package (extend the
  existing load tests).
- AC-3 is enforced by the existing package layout; keep it that way.
- AC-5–AC-8 are GUI behaviors: excluded from automated tests per
  test/README.md (GTK layers are manually verified). Keep any new sizing
  logic that is pure (e.g. a min/cap height computation) in a small
  GUI-free helper if it grows beyond a trivial expression, so it can be
  unit-tested.
- Do not weaken or delete existing tests; update the ones that referenced
  the removed height field.

## Out of Scope

- `window.width` behavior changes (stays configurable, default 400)
- Any new config setting (no max_height option)
- Scrollbars or any overflow UI beyond clipping
- Warning/deprecation messaging for the ignored `height` key
