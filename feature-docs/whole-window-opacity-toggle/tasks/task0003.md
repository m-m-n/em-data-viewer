# Task Plan: task0003 — Resolve the duplicated effective-opacity selector

## Goal

The integration branch compiles again: the effective-opacity selector exists
exactly once in the style layer, with the contract pinned in IMPLEMENTATION.md
Shared Components unchanged and every existing test still passing.

## Requirements

FR4, FR5, NFR2

## Origin

task0001 and task0002 were implemented in parallel. task0001 owns
`internal/ui/style.go` and built the effective-opacity selector there.
task0002, whose worktree forked before task0001 had committed anything, built
the same contract in the same file as a reported plan deviation so its apply
step could call the shared contract rather than duplicating selection logic in
the frame layer.

Both additions landed in textually separate regions, so git merged them
without reporting a conflict, and the merged result declares the selector
twice. The integrated build fails with:

```
internal/ui/style.go:242:6: EffectiveOpacity redeclared in this block
        internal/ui/style.go:209:6: other declaration of EffectiveOpacity
```

This is the parent-side-adoption resolution that the merge could not perform
on its own.

## Scope

### Files to Create

None.

### Files to Modify

- `internal/ui/style.go` — remove the duplicate selector and its private
  helpers, leaving one implementation.

## Design

### Which implementation survives

Keep the implementation that task0001 wrote — the one whose private parser is
already exercised directly by the existing tests in
`internal/ui/style_test.go`. It reads each key's built-in default from the
window style defaults table, so the defaults have a single source.

Remove the second implementation that task0002 added, together with the two
private helpers introduced only to support it: the key/default lookup helper
and the second parser. Nothing outside the removed block references them —
verify this rather than assuming it, and if a reference does exist, repoint it
at the surviving implementation instead of keeping the duplicate.

### What must not change

- The exported selector's name, parameter order and return type stay exactly
  as they are: the frame layer's apply step already calls it, and that call
  site is out of scope here.
- The behavioral contract is unchanged in every respect — key selection by the
  active-pattern flag, per-key fallback on a missing, unparsable or
  out-of-range value, no consultation of the unselected key, no mutation of
  the input map, result always within the inclusive range 0.0–1.0.
- No test is deleted, weakened, or rewritten to fit the surviving
  implementation. If a test fails after the removal, the removal is wrong.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: The effective-opacity selector is declared exactly once in the
      style layer.
- [ ] AC-2: No unreferenced private helper is left behind by the removal, and
      no reference to a removed helper remains anywhere in the package.
- [ ] AC-3: The full build succeeds and the full test suite passes, with no
      test file modified by this task.
- [ ] AC-4: The surviving selector still satisfies its contract: it returns
      the primary key's value when the active flag is false and the alternate
      key's value when true; a missing, unparsable or out-of-range value for
      the selected key yields that key's built-in default without consulting
      the other key; the input map is not mutated.

## Test Notes

The existing tests in `internal/ui/style_test.go` and
`internal/ui/window_test.go` already cover AC-4 in full — this task adds no
new test and changes no existing one. AC-1 and AC-2 are structural properties
best confirmed by searching the package for the removed identifiers; AC-3 is
the build and test commands passing.

Because no behavior changes, the usual write-the-test-first cycle does not
apply here: the failing signal that starts this task is the compiler error,
and the passing signal that ends it is the same build and test run succeeding
with the untouched test files.

## Out of Scope

- Any change to `internal/ui/window.go` or either test file.
- Any change to the design tokens, the sample config, or the defaults table.
- Renaming or re-signature-ing the selector.
- Refactoring beyond deleting the duplicate and its now-unused helpers.
