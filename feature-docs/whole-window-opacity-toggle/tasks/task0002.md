# Task Plan: task0002 — Whole-window opacity state, apply path, and Ctrl+T retarget

## Goal

The frame tracks which opacity pattern is active, applies the selected opacity
to the window widget so the entire window — text included — fades, and
`Ctrl+T` switches between the two patterns; the stylesheet path no longer
knows about the toggle.

## Requirements

FR5, FR6, FR7, FR8, FR9, FR10, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify

- `internal/ui/window.go` — active-pattern state field, the apply step that
  sets the window widget's opacity, wiring that step into the settings-apply
  path and the key handler, removal of the stylesheet-side pattern
  composition, and the identifier rename described in IMPLEMENTATION.md
  Conventions.
- `internal/ui/window_test.go` — tests for the state flip, the apply-path
  composition, the reload behavior, the stylesheet's independence from the
  active pattern, and the unchanged key match rule; removal of the tests that
  assert the background-color switching behavior.

## Design

### Active-pattern state

The frame keeps a single boolean field: false means the primary pattern,
true means the alternate one. It is initialized to false at construction
(FR6) and is never written into the merged style map and never persisted
(D2 in IMPLEMENTATION.md). A dedicated flip helper negates it in isolation
from any GTK call, so the flip sequence stays unit-testable.

### Apply step

A frame-level step that reads the currently effective opacity — by calling the
selector contract pinned in IMPLEMENTATION.md Shared Components with the
merged style map and the active flag — and assigns it as the window widget's
opacity property.

Called from exactly two places (D3):

1. The settings-apply path, after the style map has been re-merged. This
   covers both initial construction and every runtime config reload, which is
   what makes the reloaded values take effect for whichever pattern is active
   (FR9).
2. The key handler, immediately after the flip (FR7).

It must be safe to call before the window has been realized or presented: it
only assigns a property on an object that exists from construction time.

### Stylesheet path

The indirection that composed the active background pattern into the style map
before building the stylesheet is removed, along with its call site: the
restyle step builds the stylesheet from the merged style map directly, exactly
as it did before the previous feature. After this change the stylesheet output
is a function of the merged style map alone and is unaffected by the active
pattern (D1).

The apply step must not call the restyle step: toggling is a property
assignment only, with no stylesheet reload, no re-measure, no re-fit and no
re-pack, so window geometry cannot change as a side effect (NFR3).

### Key controller

The existing window-level key controller stays as it is structurally: capture
phase, claiming the event only when the match predicate accepts it, leaving
every other event unclaimed so drag-to-move, the context menu and blocked
scroll gestures keep working. Its match rule — the `t` keyval in either case
with Control held and neither Alt nor Super — is unchanged (FR8). The only
change is what the handler invokes: the flip plus the apply step instead of
the flip plus a restyle.

### Renames

Apply the identifier and comment rename fixed in IMPLEMENTATION.md
Conventions: every symbol and comment that names the background pattern is
renamed to name the opacity pattern. This is a mechanical rename with no
behavioral change; references to the previous task numbering in comments
should be updated or dropped so comments do not point at a superseded design.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: A freshly constructed frame reports the primary pattern as
      active.
- [ ] AC-2: The flip helper alternates the active pattern false → true →
      false across successive calls and does not modify the merged style map.
- [ ] AC-3: The effective opacity the frame would apply is the primary
      configured value when the primary pattern is active and the alternate
      configured value when the alternate pattern is active, for a frame whose
      style map carries both values.
- [ ] AC-4: Re-applying settings with new style values while the alternate
      pattern is active leaves the alternate pattern active and yields the
      newly configured alternate opacity as the effective value.
- [ ] AC-5: The stylesheet built by the frame is byte-identical for both
      values of the active pattern (the toggle no longer affects CSS), and the
      window's background color in that stylesheet is the configured primary
      background in both cases.
- [ ] AC-6: The key match rule still accepts the lowercase and uppercase `t`
      keyval with Control held, and still rejects Control+Alt, Control+Super,
      Control with an unrelated key, and `t` with no Control.
- [ ] AC-7: No symbol or comment in the modified files names a "background
      pattern"; the background-pattern selection helper is no longer called
      from anywhere in these files.
- [ ] AC-8: The whole test suite passes and the build succeeds.

## Test Notes

The state flip, the effective-value composition and the stylesheet comparison
are all reachable without a display by constructing the frame's style map
directly and exercising the pure parts, which is how the package's existing
window tests are written — follow that pattern rather than introducing a GTK
test harness.

The actual property assignment on the GTK window is the one step that cannot
be asserted headlessly; keep it as a one-line call at the edge so everything
around it is covered, and cover the visible outcome by the manual verification
items in VERIFICATION.md instead.

AC-4 is the reload regression: build the frame's state as if a reload had
occurred (re-merge with different values while the flag is set) rather than
driving the file watcher.

For AC-5, comparing the two stylesheet strings directly is the clearest
assertion and also guards against a future reintroduction of the CSS-side
toggle.

This task depends on the selector contract from IMPLEMENTATION.md Shared
Components. Tasks run in parallel, so implement against that contract as
stated; do not read the sibling task's plan.
