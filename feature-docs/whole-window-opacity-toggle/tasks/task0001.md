# Task Plan: task0001 — Opacity values, tokens, and the selection rule

## Goal

The style layer carries two configurable window opacity values with built-in
defaults, interprets them safely, and exposes a pure rule that picks the one
matching the active pattern — while the previous feature's alternate-background
value and its selection helper are removed.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR10, NFR1, NFR2

## Scope

### Files to Create

None.

### Files to Modify

- `internal/ui/style.go` — add the two opacity keys to the window style
  defaults table; add the pure opacity parser and the effective-opacity
  selector; remove the alternate-background default and the
  background-pattern selection helper.
- `internal/ui/style_test.go` — tests for the new merge defaults, parsing,
  fallback and selection; extend the token/runtime drift guard to the new
  tokens and drop the alternate-background entry from it; remove the tests
  covering the deleted helper and key.
- `design-system/tokens.yaml` — add an opacity token group with the primary
  and alternate window opacity tokens; remove the alternate-surface color
  token.
- `config.yaml.example` — document the two opacity keys under
  `window.style`; remove the alternate-background documentation and value.

## Design

### Defaults table

The window style defaults gain two entries whose keys are identical to the
public config keys (no alias entry is needed, same as the primary background
key today):

| Key | Default | Meaning |
|-----|---------|---------|
| primary opacity | `"1.0"` | Fully opaque; the startup state |
| alternate opacity | `"0.45"` | The dimmed state selected by the toggle |

The alternate-background entry is removed from the same table. The primary
background value is left untouched.

Because the merge step discards keys absent from this table, adding these two
entries is what makes the config keys effective, and removing the
alternate-background entry is what makes a stale user setting inert.

### Opacity parser

A pure function taking a configured string and a fallback float, returning a
float. Contract as pinned in IMPLEMENTATION.md Shared Components: it accepts
a decimal number within the inclusive range 0.0–1.0 and returns it; for
anything else — empty string, non-numeric text, a number below 0.0 or above
1.0 — it returns the supplied fallback. It never reports an error and never
panics. Surrounding whitespace in the configured value is tolerated, matching
how other style values are read.

### Effective-opacity selector

A pure function taking the merged window style map and the active-pattern
flag, returning the opacity to apply. Contract as pinned in IMPLEMENTATION.md
Shared Components. Behavioral description:

1. Choose the primary opacity key when the flag is false, the alternate key
   when it is true.
2. Read that key from the map; a key absent from the map behaves the same as
   an unusable value.
3. Run the parser on the value with that key's built-in default as the
   fallback.
4. Return the result. The input map is not modified, and the key that was not
   selected is not consulted at all.

This is the only component task0002 depends on.

### Design tokens

The token file gains a role-based opacity group with one token for the primary
window opacity and one for the alternate window opacity, each carrying the
same value as the corresponding defaults-table entry and a description saying
which runtime pattern it backs and that the alternate one is the dimmed state
selected by the key toggle. The alternate-surface color token is removed,
since nothing selects it any more.

The existing drift-guard test compares the tokens file against the defaults
tables; it must be extended so both new tokens are covered and the removed
color token is no longer expected. Keeping the guard honest is what prevents
the token file and the runtime defaults from diverging.

### Config sample

The sample config documents both opacity keys under the window style section,
stating the accepted range and that the second value is what the key toggle
switches to. The alternate-background key and its comment are deleted from the
sample.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1: Merging a config that sets neither opacity key yields the primary
      opacity `"1.0"` and the alternate opacity `"0.45"`.
- [ ] AC-2: Overriding either opacity key individually is reflected in the
      merged map and leaves the other key at its default.
- [ ] AC-3: The parser returns the parsed value for well-formed decimals in
      range, including the boundaries `0.0` and `1.0`.
- [ ] AC-4: The parser returns the supplied fallback for unparsable input
      (at least: an empty string and non-numeric text) and for out-of-range
      numbers (at least: one below 0.0 and one above 1.0).
- [ ] AC-5: The selector returns the primary key's value when the active flag
      is false and the alternate key's value when it is true, for a map
      carrying valid values for both.
- [ ] AC-6: The selector falls back to the selected key's built-in default
      when that key is missing or unusable, without consulting the other key,
      and without mutating the input map.
- [ ] AC-7: The drift-guard test fails if either new opacity token's value in
      the token file disagrees with the defaults table, and passes when they
      agree.
- [ ] AC-8: The alternate-background key is absent from the defaults table,
      the background-pattern selection helper no longer exists, and a style
      map that still contains the alternate-background key merges without
      error (the key is ignored).
- [ ] AC-9: The sample config documents both opacity keys, no longer mentions
      the alternate-background key, and the documented values round-trip
      through the merge path.
- [ ] AC-10: The style layer still imports no GTK-related package, and the
      whole test suite passes.

## Test Notes

Every criterion here is unit-testable without a display: the parser and the
selector are pure, the defaults table is data, and the drift guard and sample
config are file reads the existing tests already model. Follow the existing
table-driven style in the package's tests.

Edge cases worth covering explicitly: both boundary values; a value with
surrounding whitespace; a value that parses as a number but is out of range
(this must fall back, not clamp); a map missing the selected key while the
other key is present and valid.

The drift guard's structure mirrors the token file's shape, so adding the new
group means extending that structure as well as the comparison table —
verify the test fails for a deliberate mismatch before trusting it.

## Out of Scope

- Anything touching the window widget, the key controller, or the frame's
  state — that is task0002.
- Changing the primary background color or any other existing style default.
- Clamping out-of-range values instead of falling back.
- Adding a config error banner or logging for unusable values.
